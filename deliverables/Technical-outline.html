Shamsy platform, steps 1 to 9: how it would be built

For the technical lead, ahead of our meeting. Every point maps to the final brief; nothing here adds scope.
Valdis Licis
29 September 2026

1Stack and delivery

  • Your stack: Next.js and TypeScript in an Nx monorepo, Supabase (Postgres, Auth, Storage), Tailwind, Vercel, GitHub Actions.
  • One pull request per milestone. Before it starts, its acceptance tests are agreed in writing with you; the PR ships them as automated tests.
  • CI on every PR: typecheck, all tests, every migration applied to a fresh database, a preview deployment. Types generated from the schema, so a renamed column breaks the build, not a screen.
  • Every migration has a down. Documentation is written with the feature.

2Money and history that never moves

  • Amounts in integer minor units with their currency. Rates as integers (parts per million); no floats anywhere money is decided.
  • Every order line, receipt and conversion stores the rate of its own day. The cost factor is frozen per shipment at the exchange (your 0.860234 example) and snapshotted onto the order line when margin is computed.
  • Settings (minimum rate, bands, limits) are versioned rows with effective_from and set_by, so a June report knows June's minimum.
  • Test: last month's report, change today's rate, run again: identical to the last pound.

3Book per event; accounts are balances

  • Each event is one movement between two accounts: customer to operating account, operating account to exchanger, exchanger to euro account. No movement skips an intermediary.
  • Balances are derived from movements, never stored and edited. Movements are append-only; a correction is a new movement.
  • "Pass-through accounts stand at zero" is a daily closing check, not a trigger, so money can sit there overnight without entries being refused.

4Roles and cost visibility in Postgres

  • Four roles from a membership table read by row level security on every table; the screen never decides access.
  • Cost prices, landed cost and margin live in a schema the application role has no grants on. Owner reports read them through functions that check the role first.
  • Warehouse policies return no financial columns at all; owner login has two-factor authentication.
  • Test: as adviser and as marketing, request costs through the API and through direct queries; every attempt is refused.

5Receipts and transaction codes

  • The transaction code is unique. The same code with the same amount is a harmless duplicate; with a different amount, both are kept and the second goes to the open-questions list for the owner. Nothing is booked until he answers.
  • Proof screenshots in a private Storage bucket named by tenant and receipt, read through short-lived signed links, never replaced; a hash spots the same image sent twice.

6Daily account capacity

  • The Sudan business day (Africa/Khartoum) is computed in the database; timestamps are stored in UTC and shown in each user's zone.
  • Receipts per account per Sudanese day are summed at entry: a warning above 15,000,000 SDG, and the 3,000,000 single-transfer cap enforced.

7Discounts, approvals and release

  • Bands compared in whole cents (discount × 100 ≤ value × 3), so exactly 3% and exactly 5% land where the brief words them.
  • Above 5%, the owner approves that exact line; the approval is consumed once.
  • Release is refused by the database unless the order is paid in full. Orders, movements and stock carry an audit trail.

8Phones on 3G

  • Every write carries an idempotency key made on the phone, so a save sent twice is one record. Saves made offline wait in an outbox and go up on reconnect.
  • Indexed, paginated lists for tens of thousands of movements; numbers are never parsed as dates.

9Going live: import and reconciliation

  • Import scripts per source (opening balances, customer balances, open orders, stock with landed cost, the ledger from the cash-register screenshots) run into staging first.
  • Every row the rules refuse, such as one code with two amounts, lands on the open-questions list for the owner to decide.
  • A reconciliation report per account and per customer against the owner's confirmed balances. Dry runs until it matches, then switch-over; the spreadsheets stop.

10Data protection

  • Supabase in an EU region on Shamsy's own paid account, with daily backups, point-in-time recovery and Supabase's data processing agreement.
  • Building and testing happen on staging with invented or masked data. Access to live personal data is limited to Shamsy's people and one person on our side in Europe.
  • A full export of all data at any time.
